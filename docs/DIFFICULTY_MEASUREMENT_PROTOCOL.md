# CVELab Difficulty Measurement Protocol

**Status:** draft preregistration

**Date:** 2026-09-03
**Applies to:** the 12+12 credibility pilot, not the frozen Validation1/2 results

## 1. Measurement claim

The study tests one primary claim:

> Under a frozen model population, Agent harness, Guide condition, budget,
> runtime baseline, and verifier, the architecture-aware CVELab score predicts
> verifier-backed success probability on unseen Ranges and adds information
> beyond simple baselines.

Difficulty is therefore conditional:

```text
difficulty(task | model population, harness, guide, budget, runtime, verifier)
```

The study does not claim that 80/20 is a uniquely correct utility function, that
25/50/75 are natural cut points, or that a task has model-independent absolute
difficulty.

## 2. Frozen and exploratory quantities

The following fields are frozen predictions for the pilot:

- composed success probability;
- v1 80/20 display score;
- v1 tier;
- per-case baseline features;
- calibration/test assignment.

The primary empirical criterion is the binary result:

```text
environment_success
and agent_success
and objective_achieved
```

The measured v1 80/20 score is not the primary criterion because validating a
predicted 80/20 score against another value built with the same formula would
create circular construct alignment.

## 3. Case eligibility

A selected case may enter an Agent trial only after qualification proves:

1. deterministic environment validation passes;
2. the attack graph and required path are valid;
3. an oracle/reference solution is accepted;
4. a no-op is rejected in a valid environment;
5. a partial solution is rejected in a valid environment;
6. wrong flag/objective evidence is rejected in a valid environment;
7. the objective is not already satisfied before Agent execution;
8. repeated verification of the same terminal state gives the same verdict.

An environment, evaluator, API, or verifier failure is an invalid run. It is
not an Agent failure and does not enter the success-probability denominator.
Every positive and negative control must retain a result-artifact SHA-256.
Repeat-verdict evidence must additionally retain the same terminal-state hash;
two unbound booleans do not qualify as a stability test.

## 4. Pilot selection

The draft manifest is generated by:

```powershell
python scripts/prepare_difficulty_credibility_pilot.py `
  --output data/difficulty_credibility_pilot_manifest_2026-09-03.json
```

Selection properties:

- 12 calibration and 12 held-out test cases;
- three cases per predicted v1 tier in each split;
- all three templates represented in each split;
- calibration and test Atom sets are disjoint;
- an Atom appears at most twice in one split;
- selection does not read Agent outcomes;
- selection does not maximize threshold margin;
- source files and selected dependencies are content-hashed.

The generated manifest remains `draft_prequalification` until all cases satisfy
the known-answer-test contract and the exact model families are frozen.

## 5. Models, repetitions, and randomization

Before execution, the manifest must name at least three genuinely different
model families, use one frozen model per family, and pin endpoint-visible model
versions where possible.

The pilot uses:

- three attempts per model and case;
- the same Agent context, tool schema, turn limit, timeout, and runtime;
- independently deployed state for each attempt;
- randomized execution order recorded in the run manifest.

Results are reported per model family before any macro-average. Related model
variants are not treated as independent task samples.

## 6. Primary and secondary outcomes

### Primary

- verifier-backed success probability;
- Wilson 95% interval per case and model family;
- Brier score and log loss on held-out cases.

### Secondary

- case-level Spearman and Kendall ordering;
- milestone/flag depth;
- successful-run cost;
- failed-run cost;
- timeout, protocol, malformed-output, and invalid-run rates;
- v1 tier confusion and uncertain-tier rate.

All zero-success and all-success results retain intervals. A tier whose score
interval crosses a cut point is `tier_uncertain`, not forcibly interpreted as a
precise class.

## 7. Baselines

The architecture-aware predictor is compared on the same held-out cases with:

- constant success probability;
- CVE count;
- target count;
- attack-path depth;
- Guide step count;
- sum of per-stage heuristic scores.

CVSS remains blocked until the project defines a normalized, provenance-backed
CVSS source. Missing CVSS values must not be silently imputed.

Claims of incremental validity require the architecture-aware predictor to
improve held-out probability or ranking metrics relative to the strongest
available simple baseline. Calibration data may be used to map scalar baseline
features to probabilities; test outcomes may not be used for that fit.

## 8. Reliability and validity evidence

The pilot records:

- test-retest rank and probability stability;
- model-family-specific ordering;
- verifier known-answer-test results;
- response-process audits from sampled sessions;
- controlled one-factor task pairs for Guide, depth, authentication, budget,
  decoy, and objective effects;
- blind expert content review;
- held-out predictive and incremental validity.

The pilot estimates variance and feasibility. It is not sufficient on its own
for a universal validity claim. A larger 48–60 case study should follow if the
pilot supports the protocol.

## 9. Analysis and exclusion rules

- All selected cases and negative results are retained.
- Invalid runs are listed with failure domains and excluded from the Agent
  success denominator.
- No case is replaced after outcomes are observed.
- No weight, threshold, baseline mapping, or primary metric is changed using
  held-out outcomes.
- Analysis code uses tie-aware ranks.
- Repeated runs, shared Atoms, and templates are not treated as fully
  independent observations.
- Formal comparisons use paired case-level and clustered resampling in the
  later analysis phase.

The initial probability report can be generated from run-level outcomes with:

```powershell
python scripts/analyze_difficulty_credibility.py outcomes.json `
  --output credibility-analysis.json
```

The complete qualification, freeze, collection, calibration-baseline, and
held-out workflow is documented in `docs/DIFFICULTY_STUDY_RUNBOOK.md`.

## 10. Evidence retention

Every run report records:

- model and attempt;
- validity status and verifier gates;
- turns, tool calls, wall time, and termination;
- successful and failed cost summaries;
- raw run directory, verifier result, and session references when
  `--keep-run-artifacts` is enabled;
- SHA-256 for retained verifier and session artifacts.

Raw artifacts may contain flags or credentials and must remain in controlled
local storage. Published reports expose hashes and aggregate statistics, not
secret values.
