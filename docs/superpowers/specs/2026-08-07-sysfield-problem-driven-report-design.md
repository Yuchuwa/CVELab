# sysfield 问题牵引式报告设计说明

## 目标

将 `reports/report.zh.md` 和 `reports/report.en.md` 重写为立场一致的双语科研报告。报告应面向防御者、benchmark 设计者和平台方，说明为了刻画前沿网络安全智能体在真实防御环境中的风险边界，需要怎样的 benchmark 与证据体系。

报告不以优化攻击战术为目的。受控攻击轨迹只是测量手段，用于评估攻击完成度、防御可见性和抗干扰能力。

## 第一性原理叙事

中英文报告必须遵循同一条因果链：

1. **领域变化：** 网络安全智能体评测正在从静态知识和孤立任务，转向真实系统中可执行、长程、连续的行动。
2. **现有缺口：** 现有 benchmark 已经能有效测量 PoC、flag、patch 和 objective，却很少测量真实防御能否观察或扰动攻击过程。
3. **真正挑战：** 真实防御环境中的联合评测必须解决四个相互关联的问题：异构 CVE 如何组成可复现、可判定的多层任务；model、harness 和环境的影响如何分开；攻击完成度与防御可见性如何同时衡量但不相互替代；signal miss 如何解释而不被直接当作防御盲区。
4. **关键洞察：** 智能体风险不能由单一攻击成功率刻画。防御者需要攻击完成度、防御可见性和抗干扰能力的联合画像。
5. **解决方法：** sysfield 通过 CVE 原子化与多层场景编排构造真实网络任务；通过同场景控制变量对照比较 model、harness 和 decoy/noise；将攻击结果验证与运行时行为观测结合起来，分别测量攻击完成度和防御可见性；再通过预期行为覆盖分析解释 missing signal 的分布。
6. **实验证据：** 实验首先测量智能体能否完成三层攻击以及模型差异，再考察 harness 与 decoy 如何改变能力，随后评估各实验臂是否触发防御 signal，最后分析最容易未被观测的预期攻击行为。
7. **研究边界：** 结论仍受 partial run、observe-only 检测、模型与难度差异、行为规则覆盖范围，以及当前 high-decoy 实验中的 topology-hint 混杂因素限制。

全文反复强调的核心判断是：

> 攻击成功不等于防御失明，攻击失败也不等于风险不存在。

## 研究立场

报告的立场应与 CyberGym、CyberGym-E2E 和 ExploitGym 的负责任表述一致：

- 必须在真实任务中评测智能体，因为合成任务或单一完成度分数无法揭示现实风险和防御需求；
- 引入攻击行为是为了支持安全部署、修复、评估和防御规划；
- 明确认识网络安全能力的 dual-use 属性，但分析落点始终是防御者需要把智能体建模为一种真实攻击压力来源。

报告不得把 sysfield 描述成一种让智能体更有效、更隐蔽或更具攻击能力的方法。检测 miss 应用于改进 benchmark 和防御系统，而不能被转化为规避检测的建议。

## 核心主张

### Core Problem

网络安全智能体，在真实防御环境中仍然有效吗？

这里的“有效”是多维概念：它既包括能否完成攻击目标，也包括攻击过程对运行时防御是否可见，以及面对诱骗或环境干扰时能否维持行动。

### Defender-Centric Gap

现有网络安全智能体 benchmark 主要衡量任务完成度，例如 PoC、flag、patch 或最终 objective，但很少衡量攻击过程在真实防御环境中的可见性与可干扰性。对于网络安全业界而言，这留下了一个关键空白：如果前沿智能体进入真实网络环境，基础运行时防御是否仍能观察到关键攻击行为，诱骗和环境噪声是否仍能有效扰动其行动轨迹。

### Key Insight

对防御者、benchmark 设计者和平台方而言，智能体风险不能由单一攻击成功率刻画；更有用的评测对象，是攻击完成度、防御可见性和抗干扰能力的联合画像。只有把这三者同时纳入评测，才能判断前沿智能体在真实防御环境中的实际风险与防御暴露面。

## 挑战与技术对应

每一项研究挑战都必须由一种清楚、可复用的技术方法来解决。技术名称应让网络安全和系统研究者能够直接理解，不能只罗列项目组件，也不使用自造的方法名。

| 挑战 | 技术抽象 | sysfield 中的实现 |
|---|---|---|
| 真实 CVE 环境异构，难以稳定组合为可判定的多阶段任务 | **CVE 原子化与多层场景编排** | 将每个 CVE 封装为可独立部署、验证和复用的 atom，再组合为多层 range；使用阶段性 flag 和外部 verifier 判定推进结果 |
| model、harness 和环境同时影响结果，难以判断差异来自哪里 | **同场景控制变量对照** | 对同一批 Stratified-50 case 固定对应对照内的 budget 和运行条件，每次只改变 model、harness 或 decoy/noise |
| 最终 flag 只能说明攻击是否完成，不能说明防御看见了什么 | **攻击结果验证与运行时行为观测相结合** | external verifier 判断分层 flag 和 objective；SysArmor 独立记录运行时 signal；两类结果按 case 对齐但分别统计 |
| signal miss 的含义不明确，不能直接判断是行为没有发生还是防御没有看见 | **预期行为覆盖分析** | 定义 case-level expected behavior，统计 expected-signal hit 和 missing signal，并结合攻击阶段、model 与 timeout 分层分析 |

这四项技术形成递进关系：

```text
CVE 原子化与多层场景编排
  -> 同场景控制变量对照
  -> 攻击结果验证与运行时行为观测相结合
  -> 预期行为覆盖分析
```

其中前三项构成 sysfield 的主体方法，第四项用于分析防御观测边界。

## 相关工作组织

相关工作不能只比较 CyberGym、CyberGym-E2E 和 ExploitGym，也不能按论文发布时间逐篇罗列。正文应按评测对象的演进组织，说明每一类工作把什么能力变得可测量，以及为什么这种推进仍不足以回答 sysfield 的核心问题。

### 能力评测的演进谱系

| 评测路线 | 代表工作 | 主要推进 | 仍未回答的问题 |
|---|---|---|---|
| 安全知识与交互式挑战 | CyberSecEval、Cybench、InterCode-CTF | 从静态安全知识与代码风险题，推进到带执行反馈的工具交互和 flag 验证 | CTF 任务完成不能直接说明 agent 在真实软件、网络拓扑和运行时防御中的表现 |
| 真实漏洞发现与复现 | CyberGym、SEC-Bench Pro、BountyBench、OSS-Fuzz 类评测 | 使用真实代码库、历史漏洞或 bug-bounty 任务测量漏洞定位、PoC 生成和可执行验证 | 评测通常终止于漏洞发现、复现或修复，不能说明漏洞能否形成多阶段网络行动，也不观察既有防御看见了什么 |
| 漏洞生命周期与利用形成 | CyberGym-E2E、ExploitBench、ExploitGym | 将发现、PoC、patch 和回归测试串成生命周期，或把漏洞触发推进到利用原语和未授权执行 | 能力阶梯和最终 exploit 仍以攻击结果为主，不能代替对真实防御可见性与环境干扰效应的测量 |
| 远程目标与多阶段网络行动 | AutoPen-Bench、CVE-Bench、WebExploitBench、OpenAI Cyber Range、UK AISI `The Last Ones` / `Doing Life` | 从源码内漏洞任务推进到隔离远程目标、连续步骤和长程网络行动，并使用外部状态或阶段进度判断结果 | 任务可以更长、更接近部署环境，但公开协议仍很少把攻击完成度与运行时防御证据放在同一 case 中对齐 |
| 长时程漏洞研究 | VulnLMP | 把评测时间从单次 episode 延伸到持续数日的并行漏洞研究 | 长运行时间不等于多主机攻击链，也不直接说明已部署防御能否观察 agent 的行为 |
| 自主防御与防御产物 | AIxCC、CTI-REALM | 在真实基础设施代码上自动发现并修复漏洞，或从威胁情报生成可验证检测规则 | 完成漏洞修复或生成检测规则，不等于测量现有运行时防御面对攻击 agent 时的实际可见性 |

这六条路线不是由低到高的统一排行榜。它们分别测量安全知识与交互、漏洞发现与复现、漏洞生命周期与利用形成、远程网络行动、长时程研究以及自主防御产物，任务起点、终点与判定语义不同。正文不得直接比较不同 benchmark 的原始成功率，也不得把“运行更久”写成“覆盖更多攻击阶段”。

Fugu-Cyber、前沿模型 system card 以及同一模型在不同 harness 下的公开结果，应作为横跨上述路线的系统级证据使用：它们说明实际成绩属于 `model × harness × tools × environment × budget` 的联合系统，而不是裸模型常数。METR Time Horizon 只用于解释长程任务的时间尺度，不作为网络安全攻击阶段覆盖的替代指标。

### 代表工作的挑战与技术抽象

每项工作都要提炼其解决挑战所使用的领域内通用技术，而不是只复述数据集名称或项目组件。正文优先保留下表中与论证链直接相关的代表工作；篇幅不足时可以合并同类项，但不得删除从交互任务到多阶段网络行动的演进关系。

| 工作 | 主要挑战 | 技术方法 | 主要测量对象 | 相对 sysfield 的边界 |
|---|---|---|---|---|
| CyberSecEval | 将分散的安全知识、代码风险和攻防能力转化为可重复比较的模型评测 | 分类型任务集与风险导向评分 | 安全知识、代码安全与危险能力 | 以题目或子任务为主，不刻画真实多层环境中的运行时防御证据 |
| Cybench / InterCode-CTF | 让模型在可控条件下使用工具完成专业安全任务 | 容器化交互环境、执行反馈与 flag 判定；Cybench 进一步使用子任务分解记录进展 | 工具使用、CTF 完成度与中间进展 | 任务语义主要来自 CTF，不能等同于真实企业网络中的连续行动与防御观测 |
| CyberGym | 规模化构造真实漏洞任务，并可靠判断 PoC 是否复现指定漏洞 | 自动化 benchmark 构建、补丁前后 differential testing 与开放式评测 | 真实代码库中的漏洞复现和 PoC 生成 | 终点是可验证 PoC，不要求形成跨主机攻击链，也不测量运行时防御可见性 |
| SEC-Bench Pro | 在不暴露原始 PoC、补丁和详细漏洞报告的条件下测量真实漏洞再发现 | 隐去漏洞制品、真实历史版本重建与跨版本可执行验证 | 大型软件中的开放式漏洞发现与 PoC | 聚焦漏洞发现和复现，不测量后续网络推进、干扰或防御观测 |
| BountyBench | 在接近真实漏洞奖励计划的任务中同时考察漏洞利用与修复 | 真实 bug-bounty 任务重建、可执行 exploit/patch 评测 | 漏洞发现、利用与修复能力 | 将现实影响带入评测，但不以多层网络行动和既有防御的行为证据为主要对象 |
| CyberGym-E2E | 覆盖完整漏洞生命周期，并同时验证 patch 的安全性与功能正确性 | 端到端任务串联、可复现环境重建、漏洞验证与 regression testing | discovery、PoC、patch 和功能回归 | 解释生命周期阶段能力，但不回答攻击过程何时被运行时防御观察或被环境干扰 |
| ExploitBench | 避免把“触发崩溃”与“形成完整利用”压成一个二元结果 | 利用能力阶梯、阶段性可验证 checkpoint 与 harness 对照 | 从漏洞触发到利用原语和代码执行的阶段能力 | 能力分解仍发生在单个软件利用语境，不覆盖多主机推进和防御侧 signal |
| ExploitGym | 区分漏洞触发与真实攻击效果，并确认 agent 使用了指定漏洞 | execution-based evaluation、two-stage validation 与 mitigation ablation | 用户态、V8 和内核漏洞的未授权执行 | 测量 exploit 与 mitigation 的关系，但不把运行时检测、missing signal 和 decoy 干扰作为统一证据层 |
| AutoPen-Bench | 在隔离目标中标准化自主渗透测试，而不依赖人工逐步操作 | 可复现远程目标、统一工具执行与分阶段任务判定 | 侦察、漏洞利用与后续权限推进 | 覆盖远程行动，但不以真实运行时防御的 signal 覆盖和干扰效应为主要指标 |
| CVE-Bench / WebExploitBench | 在无源码或隔离远程目标上可靠判断真实 Web 漏洞是否被利用 | 隔离的真实应用、黑盒远程交互与外部状态验证 | 远程漏洞识别、利用和目标状态改变 | 主要到达单目标利用结果，不系统测量多层拓扑中的推进和防御可见性 |
| OpenAI Cyber Range / UK AISI 长程评测 | 测量 agent 能否把多个步骤串成持续的网络行动 | 仿真网络场景、长程任务编排、最终目标与最深步骤判定 | 多步骤网络行动、阶段进展与端到端目标 | 已覆盖连续行动，但公开结果没有系统给出同一攻击窗口内的运行时 signal 和预期行为 miss |
| VulnLMP | 让 agent 在加固真实软件上持续开展超长程漏洞研究 | 长时程研究 harness、多方向并行探索与可复现证据验证 | 多日漏洞研究和受控利用原语 | 时间跨度长但不必然构成多主机攻击链，也不直接评估已部署防御的可见性 |
| AIxCC | 在大规模真实基础设施软件上自主发现并修复漏洞，同时验证结果没有破坏正常功能 | 竞赛级真实代码库、可执行漏洞验证、补丁安全性与功能正确性测试 | 自主漏洞发现、PoV 和 patch | 面向自主防御生命周期，不测量攻击 agent 在运行时防御面前的暴露和受扰动程度 |
| CTI-REALM | 将威胁情报转化为可验证、可部署的防御产物 | CTI 到检测规则的任务流水线与规则验证 | 检测规则生成能力 | 评测 agent 生成防御内容的能力，而非现有运行时防御对攻击 agent 的实际观测覆盖 |
| sysfield | 在真实多层防御环境中分开测量攻击能力、防御可见性和抗干扰表现 | CVE 原子化与多层场景编排、同场景控制变量对照、攻击结果验证与运行时行为观测、预期行为覆盖分析 | 分层攻击完成度、系统条件效应、运行时 signal 与 expected-signal miss | 当前仅支持 observe-only 结论；harness 对照、更多模型与更完整行为覆盖仍待补充 |

### 相关工作的论证落点

相关工作最终应收束为三个判断：

1. 现有工作已经成功把网络安全智能体评测从静态知识推进到真实代码、真实 exploit 和长程网络行动，sysfield 不以此否定或替代这些贡献。
2. 现有工作也表明 benchmark 结果属于完整智能体系统，必须报告 harness、工具、预算、环境和判定方法；这直接支持 sysfield 的同场景控制变量对照。
3. 尚未被系统回答的是：当 agent 在具有基础运行时观测和诱骗条件的多层网络中行动时，攻击完成度、防御可见性和抗干扰表现如何在同一实验体系内分别测量并联合解释。

因此，正文不能把 sysfield 的 novelty 写成“任务更真实”“攻击链更长”或“能测更多 flag”。它真正补充的是一个 defender-centric evaluation axis：把已有工作成熟的任务完成度测量，与同场景下的运行时行为观测和干扰对照连接起来，同时保持三类证据互不替代。

### 引用与证据边界

- 研究 benchmark 优先引用原始论文、官方数据集或项目页；技术方法以公开协议为准，不从二手综述反推实现。
- OpenAI Cyber Range、UK AISI 长程任务、SEC-Bench Pro 和 VulnLMP 等未完整公开实现的评测，只描述 system card 或官方页面明确披露的任务与指标；基础设施、验证器和轨迹未披露时必须明确标注。
- Fugu-Cyber 与模型 system card 用于说明 cyber capability 和 harness dependence 的现实背景，不能替代 peer-reviewed benchmark 的方法证据。
- BountyBench、CyberGym-E2E 等同时跨越多个类别的工作，应按本文实际引用的技术贡献归类，不为了让表格互斥而削弱其任务范围。
- 相关工作比较的是研究问题、任务起终点、判定语义与证据类型，不依据不同论文报告的原始成功率建立排行榜。

## 证据架构

实验批次不是研究维度，而是实验变量的具体组合。所有实验均在引入 SysArmor 的真实防御环境中运行，因此防御可见性不是某一个批次独有的属性，而是贯穿全部实验的统一观测层。整体证据架构如下：

| 类型 | 内容 | 作用 |
|---|---|---|
| 实验变量 | model、harness、decoy/noise | 解释智能体能力和行为轨迹为何变化 |
| 统一实验底座 | CVELab Stratified-50、明确记录且在对应对照内受控的 budget 与运行协议、SysArmor | 保证每项对照的攻击结果与防御观测来自同一受控环境 |
| 攻击结果 | t1/t2/t3 flag、三旗全通、objective、timeout、失败阶段 | 衡量多层攻击完成度及不同模型系统的能力差异 |
| 防御结果 | attack-window signal 数量、产生新增 signal 的 case 比例、strict expected-signal hit | 衡量智能体行动是否触发基础运行时防御信号 |
| 防御边界 | missing signal 的类别与分布 | 定位最容易未被观测的预期攻击行为，但不直接把 miss 等同于防御盲区 |

在这一架构中，环境有效性、攻击完成度、业务目标、防御可见性和干扰效果必须分别统计。这种“证据解耦”是评测协议的设计原则，而不是一组独立实验。

报告必须为每个数字保留对应的实验配置，不得把不同模型、harness、L1/L2 context 和 decoy/noise arm 直接聚合成一个成功率。Kimi-K3 与 DeepSeek-V4-Pro 的 L2 实验采用相同参数，区别仅为模型，因此用于测量模型能力差异；DeepSeek L1 none/high-decoy 采用配对设计，用于测量当前 decoy 配置的抗干扰效应。

## 结果组织

实验评估章节按四个层层递进的研究问题展开，而不是复述各批次运行过程。

### RQ1：智能体能否完成多层攻击任务，不同模型之间有何差异？

使用三层 flag 获取率作为最直观的能力测量，并同时报告三旗全通、objective、timeout 与失败阶段。在相同参数、相同 harness 和相同 range 下，只改变 Kimi-K3 与 DeepSeek-V4-Pro，以测量模型能力差异。DeepSeek 当前只完成 40/50，因此现阶段比较必须标注为 partial，不能形成最终模型排名。

### RQ2：智能体能力会被系统条件改变多少？

该问题包含两个方向：

- **正向干预：** harness 能带来多大收益。该对照实验目前待补，在当前报告中只能作为研究问题和未来实验设计，不能提前给出结论。
- **负向干预：** decoy/noise 会造成多大扰动。DeepSeek L1 none/high-decoy 配对实验用于比较 flag、objective、timeout、行动耗时与 decoy interaction。

harness 与 decoy 都用于说明智能体能力不是模型常数，但二者作用机制相反，必须分别报告，不能合并为一个效应量。

### RQ3：智能体行动是否会触发防御信号？

SysArmor 是全部实验共有的观测层。原则上应在所有 `model × harness × interference` 实验臂上横向比较：

- 至少产生一个新增 attack-window signal 的 case 比例；
- signal 总量及每 case 分布；
- strict expected-signal hit；
- attack PASS 与 expected-signal hit 的四象限关系。

当前 Kimi-K3 L2 和 DeepSeek L2 watch-window 结果已经提供可比较的 signal accounting。DeepSeek L1 decoy 实验虽然引入了 SysArmor，但现有汇总尚未提供 attack-window signal 与 expected-signal 字段；在这些数据完成导出前，正文不得为该实验臂虚构 detection 数字。

### RQ4：哪些预期攻击行为最容易未被防御观察到？

对 `missing_signal` 进行分布分析，并在数据允许时按 model、harness、攻击完成阶段和 timeout 状态分层，回答哪些 expected rule 最常缺失，以及缺失模式是否随智能体系统和实际轨迹变化。

这一问题应表述为“最容易未被观测的预期攻击行为”，而不是直接宣称“防御盲区”。missing signal 可能来自智能体没有执行对应行为、行为超出 telemetry 边界、规则没有覆盖，或 case-level expectation 对实际轨迹过强。

四个问题形成如下递进关系：

```text
智能体具备多强的攻击完成能力
  -> 这种能力是否随模型和系统条件变化
  -> 行动过程中是否会被基础防御观察到
  -> 防御最容易在哪些预期行为上保持沉默
```

每个小节先提出问题，再明确适用的实验，随后给出证据，并且只得出证据能够支持的结论。

## 必须保留的结论边界

- SysArmor 实验是 detection/observe 实验，而不是 blocking 实验；结果不能证明攻击已被阻止。
- strict expected-signal miss 不能直接证明防御失明。可能是智能体没有执行预期行为、当前 telemetry 未覆盖该行为，或 case-level expectation 对实际轨迹而言过强。
- signal hit 不能证明攻击成功、攻击严重或防御实现了阻断。
- DeepSeek L2 实验只完成 40/50，仅支持阶段性的跨模型观察。
- Kimi-K3 L2 与 DeepSeek L2 的参数保持一致，仅模型不同；当前仍需使用共同完成 case 或明确分母进行比较，不能把 50/50 与 40/50 当成完整排名。
- harness 收益实验尚未完成，当前报告只能定义其问题、指标和所需对照，不能声称已有实验收益。
- DeepSeek L1 decoy 实验引入了 SysArmor，但当前汇总没有 signal accounting；缺少导出指标不能被写成没有 signal，也不能参与 detection hit 的定量横比。
- Kimi-K3/DeepSeek L2 与 DeepSeek L1 decoy 实验的 context 和实验设计不同；它们回答不同问题，不能直接排名。
- 当前 none/high-decoy 两个 arm 的 worker 并行度不同，high arm 还包含 serialization bug 导致的 topology-hint 差异。因此实验测量的是当前 high 配置的整体 operational effect，而不是 container decoy 的独立因果效应。
- 基于 transcript 的 decoy interaction 只是诊断证据，不是 packet-level provenance。
- 当前结果基于一份 manifest 和有限的模型智能体系统，不能建立普遍适用的模型或防御排名。

重写应保留当前草稿中有效的技术内容，删除过期的 `39/50` 数字，纳入截至 2026 年 8 月 7 日的实验汇总，并在实验章节中保留各源实验报告的可追溯入口。

## 验收标准

- 摘要以紧凑形式覆盖问题、缺口、挑战、方法、证据、启示和边界。
- 引言优先建立 defender-centric gap 和 key insight。
- 相关工作覆盖安全知识与交互任务、真实漏洞发现与复现、漏洞生命周期与利用形成、远程多阶段网络行动、长时程漏洞研究、自主防御与防御产物六条路线。
- 相关工作为代表性 benchmark 提炼可识别的技术方法，并明确每类方法能够测量什么、相对 sysfield 仍缺少什么。
- 相关工作把 sysfield 定位为对防御证据维度的补充，而不是 offensive leaderboard；不得用跨 benchmark 原始成功率进行排名。
- 方法章节明确说明各系统组件如何解决前文提出的挑战。
- 实验结果按研究问题组织，并为每项结果保留对应的实验配置和分母。
- RQ1 使用分层 flag 与其他攻击结果回答攻击能力和模型差异。
- RQ2 明确区分待补的 harness 收益实验与已有的 decoy 干扰实验。
- RQ3 把 SysArmor 作为全部实验的统一观测层，只报告已完成 signal accounting 的实验臂。
- RQ4 使用 missing-signal 分布分析防御沉默边界，并避免把 miss 直接等同于盲区。
- 任何主张都不得超出上述结论边界。
- 中英文报告在结构、数字和结论强度上保持一致。
